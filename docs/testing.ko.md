# 통합 테스트 전략

이 프로젝트에서는 앱의 여러 모듈과 사용자 흐름을 함께 검증하는 전체 활동을 `통합 테스트`라고 부릅니다. 내부 명령에 `unit`이라는 이름이 남아 있어도 운영 우선순위는 아래 세 단계로 통일합니다.

## 우선순위

1. **스크립트 통합 테스트**: `npm test`
2. **Codex 브라우저 테스트**: 개발 전용 `/qa`의 `Codex 브라우저` 시나리오
3. **사용자 직접 테스트**: 청취, 실제 장치, 외부망, Electron, 다른 브라우저처럼 Codex가 신뢰성 있게 판정할 수 없는 시나리오

앞 단계가 실패하면 그 원인을 먼저 확인합니다. 다만 외부 서버 장애로 협업 항목이 `BLOCKED`인 경우 서버와 무관한 다음 항목은 계속 진행합니다.

## 시나리오 순서

각 실행 주체 안에서는 많은 기능을 한 번에 통과시키는 큰 시나리오를 먼저 실행합니다. 큰 시나리오가 실패했거나 위험 영역을 더 자세히 확인해야 할 때 집중 시나리오를 실행합니다.

- 큰 시나리오: 핵심 편집 전체 흐름, 두 브라우저 협업 전체 흐름, 실제 청취 기반 전체 재생 흐름
- 집중 시나리오: 패널, 트랙 규칙, 파트 경계값, 분할·병합, 룰러, 믹서, 파일, 서버 복구 등

기존 8개 UI suite와 추가 회귀 항목의 상세 케이스 102개는 20개 큰·집중 시나리오로 통합했습니다. 원본 케이스와 새 시나리오의 대응 관계는 `case-tests/README.md`에 유지합니다.

## 실행 방법

```bash
npm test
npm run qa
```

`npm run qa`는 Vite 개발 서버를 시작하고 `/qa`를 엽니다. QA 화면은 프로덕션 빌드의 라우트로 제공하지 않습니다. 화면에서 고정 프로젝트를 내려받아 앱 탭에 불러오고, 각 시나리오의 절차와 기대 결과에 따라 결과를 기록합니다.

## 기준 환경

- Codex 인앱 Chromium 뷰포트: 1280×720
- 측정 DPR: 1.5
- 사용자 확인: Firefox, 실제 사용 창 크기, 80%·100%·125% 확대율
- 고정 데이터: `case-tests/fixtures/qa-project.json`

뷰포트가 기준과 다르면 QA 화면에 `DIFFERENT`로 표시하지만, 이는 제품 실패가 아닙니다. 해당 크기의 추가 확인으로 기록합니다.

## 서버 장애 정책

QA 화면은 시작할 때 설정된 API의 `/rooms`에 3초 제한으로 요청합니다. HTTP 상태 코드와 관계없이 응답을 받으면 서버에 도달한 것으로 판단합니다.

- API URL 없음: 서버 의존 시나리오를 `BLOCKED`
- 연결 실패 또는 3초 초과: 서버 의존 시나리오를 `BLOCKED`
- 서버 응답 있음: 자동 `BLOCKED`를 해제하고 실행 가능 상태로 복원
- 서버와 무관한 시나리오: 서버 상태와 관계없이 계속 실행

`BLOCKED`는 테스트 실패가 아니며 원인이 해결된 뒤 다시 실행합니다.

## 결과 기준

- `PASS`: 기대 결과를 모두 확인함
- `FAIL`: 제품 결과가 기대와 다름. 메모에 실제 결과와 재현 조건을 필수 기록
- `BLOCKED`: 서버, 장치, 권한, 환경 등 외부 조건 때문에 실행할 수 없음
- `NOT RUN`: 아직 실행하지 않음

결과와 메모는 브라우저 `localStorage`에 저장됩니다. 실행을 공유하거나 보관할 때는 QA 화면의 `결과 JSON 내보내기`를 사용합니다. 새 회귀 실행 전에는 `새 실행으로 초기화`를 눌러 이전 판정을 제거합니다.
